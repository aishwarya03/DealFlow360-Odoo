DealFlow360 API Reference

Everything the frontend needs to talk to the sales operations backend. Authentication, the product and customer catalog, and multi-warehouse stock are implemented and verified end to end; each feature slice adds a section here as it lands.

Route trees #

The API is split into two trees with genuinely separate authentication boundaries — not one tree with different labels.

PrefixWhoToken audience
/api/internal/* Staff: admin, sales rep, sales manager, finance dealflow360:internal
/api/portal/* Customers, for portal negotiation (not built yet) dealflow360:portal
Why this matters

The two token families are not interchangeable. A portal token sent to an internal route fails signature verification and returns 401 — it is not a role check that a future route could forget to apply.

Unprefixed utility routes: GET /health and GET /api/ping.

Response envelope #

Every response — success or failure — uses one of these shapes. Write your API client against the envelope, not against individual endpoints.

Success
{
  "success": true,
  "message": "Logged in",
  "data": { }
}
Failure
{
  "success": false,
  "message": "Invalid email or password",
  "errors": []
}

data is null when an endpoint returns no payload. errors is empty except on validation failures, which carry one entry per bad field.

Validation failure · 422
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    { "field": "email",    "message": "Must be a valid email address" },
    { "field": "password", "message": "Password must be at least 8 characters" }
  ]
}

field uses dot notation for nested paths — for example lines.0.quantity once quotations exist — so it maps straight onto form field names.

Status codes #

404Route or resource not found—
409Conflict, e.g. duplicate emailShow message on the form
422Validation failedMap errors[].field onto form fields
500Server bugGeneric error toast
Common mistake

401 means the session is gone. 403 means the session is fine but this user may not do this. Logging someone out on a 403 is a bug.

Authentication #

Login returns a JWT. Send it on every protected request.

Authorization: Bearer <token>
  • Lifetime: 7 days, set by JWT_EXPIRES_IN.
  • Claims: sub (user id, as a string), email, role, aud, iss, exp.
  • Treat the token as opaque. Read the user from /me rather than decoding it — the server re-checks the account on every call, so a deactivated user stops working immediately instead of at token expiry.
  • There is no refresh endpoint. On a 401, send the user back to login.

Products #

The catalog every quotation is built from. Reads are open to all staff — a rep cannot build a quote without them. Writes are admin-only, because the catalog is backend configuration.

Two independent axes

productType says what a product is made of — GOODS (stocked, physical), SERVICE (labor, never stocked), or COMBO (a bundle — accepted for the field, composition isn't built yet). category says where it sits in the catalog and is what a discount ceiling is configured against — see Categories below. isSubscribable is a third, separate axis: whether the product may be sold on a recurring plan. All three are independent — a SERVICE in the "Software" category can still be subscribable, for instance.

GET /api/internal/products Any staff

Returns active products, ordered by name.

includeInactivetrue · falseInclude deactivated products

marginPercent is computed server-side as (listPrice − costPrice) / listPrice × 100. Don't recompute it in the frontend — one formula, one place, so every screen shows the same figure. category.path is a breadcrumb built server-side too — one parent hop deep, matching how shallow the tree is expected to stay.

Money is numbers, not strings

Prices are stored as SQL DECIMAL, because binary floating point cannot represent 0.1 exactly and that error compounds across discounts, tax and proration. They are converted to plain JSON numbers at the API edge, so the frontend needs no decimal library.

PATCH /api/internal/products/:id ADMIN

Partial update — send only the fields that change. An empty body returns 422.

The cost-versus-list rule is re-checked against the stored record, so lowering listPrice below the existing costPrice is rejected with 400 even though the request body alone looks valid.

POST /api/internal/products/:id/image ADMIN

multipart/form-data with a single field named image. Saves the file to server/uploads/products/ under a random UUID filename and sets Product.imageUrl to the resulting path (e.g. /uploads/products/8f2c…3e1.png), which is then served statically — GET {{baseUrl}}/uploads/products/8f2c…3e1.png returns the image directly, no auth required, the same tradeoff a public CDN makes.

CodeWhen
400No file, wrong field name, not JPEG/PNG/WebP, or over 5MB
403Not an admin
404Product doesn't exist

Uploading again replaces the image: the previous file is deleted from disk once the new one is saved, so re-uploads don't accumulate orphaned files.

DELETE /api/internal/products/:id ADMIN

Soft delete. Sets isActive: false and returns the updated product. The row is never removed, because quotation lines reference it and that history has to stay readable after a product is withdrawn from sale.

Deactivated products disappear from list results unless you pass includeInactive=true.

Categories #

A real tree, not a fixed list — an admin creates categories the same way they create products. This is the unit discount ceilings are configured against (brief §A3): Hardware can allow 15% discretion while Service allows only 10%, and a product filed under either inherits the check.

A category can hold children, products, or both

parentId is nullable and self-referencing. "Hardware" can have a child category "Computers" that products attach to, while "Software" holds products directly at the root with no children at all — both are valid, which is what lets a category like "Electronics" contain sub-categories and products at the same time. Filtering products by a parent category (see categoryId above) walks the whole subtree, so filtering by "Hardware" also returns everything filed under "Hardware / Computers".

GET /api/internal/categories Any staff

Flat list, each row carrying its own breadcrumb path. Filter with search.

200 OK
{
  "success": true,
  "message": "Categories",
  "data": {
    "categories": [
      {
        "id": 2,
        "name": "Computers",
        "parentId": 1,
        "discountCeiling": null,
        "productCount": 3,
        "childCount": 0,
        "path": "Hardware / Computers"
      }
    ],
    "count": 4

}

discountCeiling is a percent, admin-set, not yet consumed by any engine — the discount risk feature will read it once built (see SOURCE_OF_TRUTH.md §3). null is intended to mean "inherit from the nearest ancestor that defines one."

GET /api/internal/categories/tree Any staff

Same data, nested: each root category carries a children array. Built for a tree-view picker; use the flat list above for a plain dropdown.

POST /api/internal/categories ADMIN
Request body
{
  "name": "Computers",
  "parentId": 1,
  "discountCeiling": null
}

name only has to be unique among siblings — "Accessories" can exist under both "Hardware" and "Software" without colliding. Errors: 400 parentId doesn't exist · 409 a category with that name already exists at the same level.

PATCH /api/internal/categories/:id ADMIN

Partial update, including re-parenting. Moving a category under its own descendant is rejected with 400 — the tree can never become a cycle.

DELETE /api/internal/categories/:id ADMIN

Hard delete — unlike products, customers and warehouses, an unused category carries no history worth preserving. Blocked with 400 if it still has child categories or products attached, naming the count, so deleting a category can never silently orphan something that pointed at it.

Customer tiers #

Tiers are rows, not an enum, and a customer's tier is calculated from their trading history — never assigned by hand.

The flow
Customer metrics  ->  Scoring engine  ->  Tier  ->  Discount rule  ->  Approval routing

Scoring

Four weighted metrics produce a score out of 100. Weights and targets are configuration.

MetricWeightFull marks at
Total purchase value40₹12,50,000
Completed orders2528
Recent purchase activity20ordered today; decays to 0 at 80 days
Customer relationship duration153 years
ScoreTierTier ceiling
0–39Bronze5%
40–59Silver10%
60–79Gold15%
80–100Platinum20%
Worked example — seeded, reproducible

Acme Corp: ₹12,00,000 spend, 24 orders, last order 12 days ago, customer 2.5 years. Scores 38.4 + 21.43 + 17 + 12.5 = 89.33 → PLATINUM, which then resolves a 20% Hardware ceiling instead of Gold's 15%.

Metrics live on the customer (totalPurchaseValue, completedOrders, lastOrderAt, customerSince) and can be set through customer create/update. They become derived from real orders once the quotation slice lands; the scoring engine itself does not change. Editing any metric re-scores that customer automatically.

Discount rules #

One configured ceiling per tier × category. No percentage is hardcoded anywhere in application code.

HardwareSoftwareService
Platinum20%20%15%
Gold15%15%10%
Silver10%10%7%
Bronze5%5%3%

Resolution

GET /api/internal/discounts/resolve?customerTierId=&categoryId= returns the governing rule. Categories are a tree, so resolution walks up from the product's own category — a product filed under "Hardware / Computers" is governed by the "Hardware" rule, and the response flags inherited: true.

If nothing matches anywhere up the chain it returns 400 naming the tier, the category and the chain it checked. A missing rule is never a silent allowance.

Approval routing

The rule
discount <= maxDiscountPercent            ->  no approval
discount >  maxDiscountPercent            ->  Sales Manager
blended risk > financeEscalationSeverity  ->  Sales Manager, then Finance

The blended risk score is each line's overage weighted by line value, spread across the order — it is what catches many small breaches that no single line makes look alarming. The Finance trigger sits on the tier, because the score is an order-wide figure no single line's rule can decide.

Worked example — the brief's own

Acme, laptop at 12% (Hardware allows 15% → fine) plus setup service at 18% (Service allows 10% → over by 8). One line breaks its own stricter ceiling, so the whole quotation routes to a Sales Manager. Blended risk = 8 × 20,000 ÷ 120,000 = 1.33, below the Finance trigger, so Finance is not pulled in.

Warehouses #

Stocking locations. Reads are open to all staff — a rep needs to know where stock sits when a customer asks about delivery. Warehouse setup is backend configuration, so writes are admin-only.

Two numbers the split algorithm needs

shippingCostPerShipment is the fixed cost of one dispatch from this location, whatever it contains. Scoring an allocation as shipments × cost means two shipments from a cheap depot can legitimately beat one from an expensive one — which is the whole point of weighting rather than just counting shipments. priority breaks ties, so an admin can say “prefer Main unless there's a real reason not to” without inventing a fake cost.

RouteMethodWho
/api/internal/warehousesGETAny staff
/api/internal/warehouses/:idGETAny staff
/api/internal/warehousesPOSTADMIN
/api/internal/warehouses/:idPATCHADMIN
/api/internal/warehouses/:idDELETEADMIN

Lists are ordered cheapest-dispatch first with priority as the tie-break — the order a split would naturally consider them in. Filters: search (name, code or city), includeInactive.

POST body
{
  "code": "WEST",
  "name": "West Depot",
  "city": "Mumbai",
  "shippingCostPerShipment": 320,
  "priority": 40
}

code is required, unique, and uppercased automatically. shippingCostPerShipment defaults to 0 and priority to 100.

Deactivation is refused while stock remains

DELETE returns 400 if the warehouse still holds anything on hand or reserved, naming the quantities. Hiding a location that physically contains goods turns a reporting problem into a lost-inventory problem.

Inventory #

Stock of one product in one warehouse. Reads are open to all staff; writes belong to ADMIN and FINANCE — the spec puts warehouse and backorder decisions with Finance/Operations, and a rep should not be able to move stock numbers to make a deal work.

Three quantities, one of them derived

FieldStored?Meaning
onHandQtyYesPhysically present in this warehouse
reservedQtyYesPromised to confirmed orders, not yet shipped. Still on the shelf, no longer sellable
availableQtyNoonHand − reserved, computed at read time
Why available is never stored

Storing all three creates two numbers that must agree forever, and eventually they would not. Everything that asks “can I promise this?” reads availableQty, including needsReorder — a location is below its reorder point on what it can still sell, because stock already promised to someone else cannot save you.

GET /api/internal/inventory/availability/:productId Any staff

The question the fulfillment split will ask: where can this product be found, and how much can actually be promised. Locations come back cheapest-dispatch first.

200 OK — laptop across three warehouses
{
  "success": true,
  "message": "Availability",
  "data": {
    "product": { "id": 1, "sku": "HW-LAPTOP-14", "name": "ProBook 14\" Laptop", "unit": "unit" },
    "totalOnHand": 12,
    "totalReserved": 0,
    "totalAvailable": 12,
    "stockedLocations": 3,
    "locations": [ ... ]
  }
}

stockedLocations is how many separate dispatches this product could involve if drawn from everywhere. Getting that number down is the split algorithm's job.

GET /api/internal/inventory Any staff

All stock rows with their warehouse and product. Filters: warehouseId, productId, lowStock=true, inStockOnly=true.

GET /api/internal/inventory/low-stock is the same worklist, already filtered and sorted worst-first.

PUT /api/internal/inventory ADMIN · FINANCE

Absolute set — “this location now holds exactly N”. For a stocktake result, or loading a new product into a warehouse. Creates the stock row if it doesn't exist.

Request body
{
  "warehouseId": 3,
  "productId": 2,
  "onHandQty": 12,
  "reorderPoint": 5,
  "reorderQty": 20,
  "reason": "Initial load"

Setting on-hand below what is already reserved returns 400 — that would mean stock has been sold that cannot be delivered.

POST /api/internal/inventory/adjust ADMIN · FINANCE

Signed change — “20 units arrived”, “3 were damaged”. Kept separate from PUT because “add 20” and “make it 20” are different operations, and conflating them is how stock goes wrong under concurrent edits.

Request body
{
  "warehouseId": 1,
  "productId": 1,
  "delta": 10,
  "reason": "Delivery GRN-4471"
}
CodeWhen
422reason missing, or delta is zero
400Would push stock negative, or below what is reserved
404No stock row yet — set an initial level first

reason is required here but optional on PUT: an unexplained correction to a balance is exactly what makes inventory untrustworthy.

GET /api/internal/inventory/movements Any staff

Append-only ledger explaining how a balance got where it is: type, signed deltas, reason, and the user who did it. Filter by warehouseId and productId. Newest first, 50 most recent.

TypeMeaning
RECEIPTStock arriving into a warehouse
ADJUSTMENTCorrection: stocktake, damage, shrinkage
RESERVATIONCommitted to a confirmed order
RELEASEReservation freed, e.g. cancelled order
SHIPMENTReserved stock physically dispatched

RECEIPT and ADJUSTMENT are produced now; the other three arrive with order fulfillment. The stock row and its movement are written in one transaction, so a balance can never change without a record explaining it.

Testing in Postman #

An importable collection covering every endpoint lives at docs/DealFlow360.postman_collection.json.

Import it

  • Postman → Import → drop in the JSON file
  • Open the DealFlow360 API collection
  • Run Auth → Login as ADMIN
No token copy-pasting

The login requests carry a test script that writes the returned token into the {{token}} collection variable, and the collection sends Authorization: Bearer {{token}} on every other request. Log in once and everything else just works. Run Login as SALES_REP to switch identity and watch the same requests start returning 403.

A run worth doing

  • Login as ADMIN → Create product → 201, and productId updates itself
  • Update product → watch marginPercent recalculate
  • Deactivate product → then List products: it's gone. List — include inactive: it's back
  • Login as SALES_REP → Create product again → 403, while List products still works
  • Create customer as the rep → 201, because customers are sales work, not configuration

Requests that are meant to fail are named with their expected status, so a red response there is the test passing.

Frontend setup #

Set VITE_API_URL=http://localhost:3000 in client/.env. Vite reads env only at startup, so restart the dev server after creating that file.

Attach the token automatically

client/src/api/client.js
apiClient.interceptors.request.use((config) => {
  const token = localStorage.getItem('df360_token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

Handle 401 globally, leave 403 to the screen

apiClient.interceptors.response.use(
  (res) => res,
  (error) => {
    if (error.response?.status === 401) {
      localStorage.removeItem('df360_token');
      window.location.href = '/login';
    }
    return Promise.reject(error);
  }
);

Unwrap the envelope once

So screens deal in payloads rather than res.data.data.

export const login = async (credentials) => {
  const res = await apiClient.post('/api/internal/auth/login', credentials);
  return res.data.data; // -> { user, token }
};

Reading errors

The server message is always at error.response.data.message and is safe to display. Field errors are at error.response.data.errors.

Rule of thumb

Hide actions a user's role cannot perform, but treat that as cosmetic. Every rule is enforced server-side — the frontend renders decisions, it does not make them.

Staff Login & Roles

How the four internal roles — Admin, Sales Rep, Sales Manager, Finance — sign in and what each one actually sees. This is the "backend ERP view": the internal shell, not the customer portal.

Overview

"Staff" means an internal User row — someone on Netrix Systems' own team. This is a different login surface from the customer portal: staff authenticate against /api/internal/auth/* with a token scoped to the internal audience, and that token is rejected outright by any future /api/portal/* route, not just hidden from it. See API.html — Route trees.

Once signed in, a staff member lands in the internal shell — a persistent sidebar, filtered to the tabs their role can reach, exactly per SOURCE_OF_TRUTH.md §6's role-to-access matrix and the brief's own role descriptions (§3).

The four roles

Every account is one of these, stored as User.role.

Admin

Backend configuration and platform-wide reporting. The only role that can write to Products and Warehouses.

Sales Rep

Builds quotations, applies discounts, tracks their own deals. Does not act as an approver.

Sales Manager

Approves discounts, configures ceilings, watches deal health. First approval step.

Finance

Second-level approval, fulfillment, billing and credit notes. Can adjust stock.

Login flow

What happens between typing a password and seeing the dashboard.

  1. Staff opens /login — a screen the customer portal never shares, per the brief's requirement that the portal be "a real, separate, restricted view."
  2. Submitting the form calls POST /api/internal/auth/login. The API returns the same error for a wrong password and an unknown email, so the form can't be used to discover which emails have accounts.
  3. On success, the JWT is stored client-side and every subsequent request carries it as Authorization: Bearer <token>.
  4. The app re-fetches GET /api/internal/auth/me rather than trusting the decoded token — a deactivated account or an expired token is caught on the next request, not just at expiry.
  5. The internal shell renders with a sidebar filtered to this user's role. If the user had been redirected to /login from a specific page, login sends them back there — not always to the dashboard.
  6. A 401 from any request anywhere in the app clears the session and returns to /login. A 403 does not — that means the session is fine but this role can't do this specific thing, so it's shown as a permission message, not a logout.

What's live vs. soon

Everything under Configuration calls a real, tested API built in earlier slices. Everything under Workspace beyond Dashboard is routed and role-gated but shows a placeholder — there's no Quotation, Approval or Fulfillment backend yet for it to call.

  • Live: Products, Customers, Warehouses, Inventory — full read access for all four roles, writes gated per the table above.
  • Soon: Quotations, Approvals, Fulfillment, Subscriptions, Invoices, Deal Health, Reports.

The Dashboard is honest about this split: its four numbers (active products, active customers, warehouses, low-stock items) are all real counts. No fabricated statistics anywhere, per DEMO_SCENARIO.md's own rule for the rest of the app.

Where enforcement actually lives

Read this before trusting the sidebar

Everything on this page describing what a role "can" or "can't" do is a client-side convenience — it avoids flashing a screen the user is about to be denied, nothing more. The rule that actually matters is enforced again on the server, on every request, regardless of what the sidebar shows: authenticateInternal checks the token, authorize('ADMIN', ...) checks the role. A user who edits localStorage or calls the API directly with curl hits the exact same wall a legitimate UI click would. See API.html — Status codes for the 401 vs 403 distinction this depends on.

This mirrors SOURCE_OF_TRUTH.md §6's own framing: "Enforced server-side (middleware, not hidden nav)." The same principle will apply once the customer portal exists — a stripped DTO server-side, not a component the portal simply doesn't render.
